# Repository instructions

- Treat `readme.md` and the focused documents under `docs/` as package-consumer guidance. Keep maintenance and publication procedures in the developer and maintainer documents.
- When maintenance changes a public entry point, a host composition, a downstream integration, or a verification path, review the related consumer documentation from the perspective of current use. Treat `docs/proven-in-use.md` as optional examples, evidence, and history, not as a support entitlement or required release or adoption gate. When that page is updated, distinguish Commonlib-owned result contracts from downstream tests, real-runtime verification, and host surfaces which currently have build or type-check coverage only.
- Treat `compat/*` as an explicit migration boundary rather than an example API. Do not present a compatibility import as the recommended integration when a focused entry point exists.
- Give new design and specification documents YAML frontmatter with the document date, the Commonlib version reviewed, and the Self-hosted LiveSync version reviewed. Quote version values. When the document describes unreleased work, include a status field which makes that explicit.
- Follow the module filename conventions in [docs/development.md](docs/development.md#module-filenames): an upper-case initial for a module with a class of the same name, and a lower-case initial for a function module.
